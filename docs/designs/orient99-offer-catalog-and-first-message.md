## Problem Statement
The Orient99 sales agent answers Messenger, Instagram and website clients. It fails in two ways that cost Orient99 bookings:
1. It cannot reliably find offers that exist. Offers sit in OpenAI vector store `vs_69e4c252b3f08191a2b8c40396220d7c` as 204 long program files (14,075 offer blocks, 7,039 unique offer links, 2,946 hotels), scraped in April 2026. File search returns the right file but the wrong chunk, so a named hotel is often "not found" (ISSUE-001: Lonicera Resort & Spa reached the model in 4 of 12 tries). Hotel names are stored in Latin capitals only, so Cyrillic queries ("Лонисера") return 0 of 10 correct hits. The data has no Summer 2027 season.
2. The client's first Messenger message is often never seen by the agent. GHL's "Generate response" workflow posts `{{contact.client_response}}` to Make. On a new conversation that field is empty, so Make route 1 sends a fixed greeting and calls `GET /start`, which takes no message. In the week 26.10 to 03.11, 20 of 50 Make runs were greeting-only.

## Premises
1. ISSUE-001 is a retrieval-shape problem, not a model problem. Smaller vector chunks would raise the hit rate, but date, transport and season still depend on semantic luck.
2. Because the agent no longer quotes prices, the catalog needs identity and routing data (hotel, program, transport, season, nights, departure range, link), not authoritative prices.
3. The first message is lost in GHL before it reaches Make. Every fix needs at least one change in the Make or GHL console.
4. Doing nothing keeps wrong "no offer" handovers on existing offers and keeps dropping about 40% of first messages.

### C1. Catalog rows and sources (`data/offers.json`)
- Two row kinds. `hotel_offer`: one hotel inside one program. `program`: an excursion, tour, cruise or exotic trip sold per departure, with `hotel: null` (sources: `/ekskurzii/`, `/cruises/`, `/exotica/` program pages).
- Fields and their page:
  - From the destination page: program link.
  - From the program page: program title, destination, region, transport ("Транспорт"), departure city (from "Маршрут"), nights ("Продължителност"), `departure_dates` (the full "Дати на отпътуване" list), hotel list with hotel link, board code and image.
  - From the hotel offer page: hotel name (Latin, as on the site) and `from_price_eur` ("Цена от").
- `season`: from the program title ("Лято 2027", or a bare year); if the title has none, the year of the program's departure dates when they all fall in one year; otherwise `unknown`. The title wins over price-table dates, which can be stale.
- Links are checked at scrape time; a row whose link does not return HTTP 200 is dropped. Crawl politely: one request at a time, at least 1 s apart, 3 retries with backoff.

### C2. `search_offers` tool contract
- Inputs (all optional): `hotel`, `destination`, `transport` (plane, bus, own), `season_year`, `month`, `nights`, `board`, `budget_per_person_eur`, `kind`.
- The tool description tells the model to pass only the hotel name in `hotel` and the place in `destination`.
- Hotel matching: the query is transliterated Bulgarian → Latin, then both sides are reduced to a phonetic key. The generic-word list is applied to the key tokens after transliteration, so Cyrillic-derived spellings are caught too: HOTEL, OTEL, RESORT, REZORT, SPA, CLUB, KLUB, AND, I, &, BEACH, BICH. The key is built as follows: uppercase; drop punctuation and the generic words; C before E/I/Y → S, other C/K/Q → K, Y/I/J → I, W → V, PH → F, collapse double letters). Exact key match is `exact`; edit distance ≤ 2 on the key is `approximate`. "Лонисера" → LONISERA = key of LONICERA (C before E → S); "Камелия" → KAMELIIA → KAMELIA = key of KAMELYA.
- Token containment: when the query's key tokens and a hotel's key tokens contain one another but are not equal, the result is `approximate` with candidates, never `none` and never `exact`. There is one exception. If exactly one candidate's tokens are all inside the query tokens (e.g. "Лонисера Алания" → {LONISERA, ALANIA} ⊇ {LONISERA}), that candidate is returned as `exact` with `matched_by: containment`.
  - "Лонисера" stays exact for LONICERA RESORT & SPA (key {LONISERA}). It is approximate for LONICERA WORLD (key {LONISERA, VORLD}), whose tokens are not all in the query.
  - "Камелия" is approximate for KAMELYA SELIN.
  - "Lonicera resort and spa" is exact (RESORT, AND and SPA are dropped).
  - The matcher's unit tests carry all of these strings.
- Filters and ranking, per input:
  - Hard filters: `hotel` (through the match), `destination`, `transport`, `season_year`, `month`, `nights`, `board`, `kind`.
  - Rank only: `budget_per_person_eur`. Rows within budget come first; rows over it are flagged `over_budget`. The site's "Цена от" can be stale, so the budget never excludes a row.
  - Without a month, rows are ordered by earliest upcoming departure, then nights match, then lowest `from_price_eur`. With a month, rows are ordered by nearest departure in that month.
- When filters empty an exact hotel, the response is `match: exact`, `rows: []` and `unmet_filters: [...]` (e.g. `["transport"]`). With no `hotel` in the query, `match` is `not_requested`.
- Season and month use the departure dates when a row has them: `season_year` keeps rows with a departure in that year, and `month` keeps rows with a departure in that month. The title's season is used only for rows without dates. `season_unknown` is reserved for rows with neither a year in the title nor any dates.
- A small curated alias file covers names the phonetic key cannot reach.
- Output: `match` (`exact` | `approximate` | `none` | `not_requested`). For `exact`, only rows of the matched hotel are returned (LONICERA PREMIUM and LONICERA WORLD have different keys and are excluded). Rows pass the hard filters and are ordered as described above. At most 8 rows. For `approximate`, a list of up to 5 distinct hotel names and no offers: the agent asks the client which hotel they mean and never presents an approximate match as the requested hotel.
- `season_unknown` rows are never presented as the requested year. If nothing else matches, the agent hands over. Rows without dates come back flagged `dates_unknown`, and the agent points to the link for dates.
- The tool never returns a price amount to the model, so Part 1 rule 5 and replay check D14 stay safe.
- Board: filters on the board code from the program page.

### C4. First message: `POST /first-message`

> **Superseded on 2026-11-04.** At the engineer's request C4 was not built in code. The first message is fixed in Make instead: live scenario "Orient 99 Messenger AI" route 1 reads the contact's messages through the GHL API (read-only Private Integration token), runs /start + /chat and replies with the AxeL greeting plus the answer. On any GHL error or when there is no text it falls back to the old greeting. The catalog decisions C1-C3 and C5 stand.
- Request `{contact_id, channel}`. Response `{thread_id, response}`, the same shape `/chat` returns plus the new thread id. It never returns or logs GHL message bodies beyond what `/chat` already logs.
- Auth: the global `x-api-key` (SECURITY_API_KEY) is not enough here. main.ts enables CORS for the webchat widget on another origin, so that key is likely visible in browser code. `/first-message` also requires a separate server-to-server header, `x-first-message-secret`, checked against a new env var held only by Railway and the Make module. The engineer creates and stores that secret, never in chat. A missing or wrong secret returns 401 before any GHL call.
- Steps:
  1. Create the conversation.
  2. Read the contact's Messenger conversation through the GHL API, with a 5 s timeout inside the existing 32 s budget.
  3. Take the inbound messages after the last outbound message (at most 5, oldest first). If there is no outbound message, take the inbound messages from the last 10 minutes.
  4. Run them as one turn. Store the GHL ids of the answered messages in the OpenAI conversation's metadata.
- Fallback: on a GHL error, 401/403, 429, a timeout, or no text (sticker, image, "Get started" postback), the response is the current fixed greeting plus a valid `thread_id`. The cause is logged as a code, so greeting-only runs stay measurable.
- Dedupe:
  - What is stored: only messages answered by a real model reply. The greeting fallback and the 32 s "please wait" reply do not count. `/first-message` stores each answered message's normalised text (trimmed, whitespace collapsed, lowercased) in the conversation metadata, with a timestamp, keeping at most 5 for 10 minutes.
  - What is compared: a later `/chat` on that thread splits its incoming text into lines, because the GHL debounce chain may join several message bodies. It removes the lines whose normalised text matches a stored one, and runs the model on what is left.
  - If nothing is left, `/chat` makes no model turn and returns a single space as `response`. That is the reply Make route 8.3 already sends today for messages without letters or digits.
  - /spec checks on a test contact what GHL does with that reply. If it reaches the client or raises a GHL error, one filter (`response` is not blank) is added before the reply modules of routes 8.1 and 8.2. That is the only possible route-8 change.
  - Known limit: a client who deliberately repeats the exact same text within 10 minutes of a real answer gets no second answer.
- Make route 1 changes, done with the engineer's yes:
  - module 50 becomes `POST /first-message` with `contact_id` = the webhook's `leadID` and `channel`;
  - module 5 moves after module 50 and responds with `{{50.data.response}}`;
  - module 9 stores `{{50.data.thread_id}}`.

  Three modules, no others. Instagram is out of this sprint unless its blueprint shows the same route 1, decided in /spec.

### R2-3 — feasibility (blocking)

### R2-5 — completeness (blocking)
